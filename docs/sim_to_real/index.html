从模拟到真机：GLM-5.3-Flash NVFP4 PP4 on B200 的实现与对齐

GLM-5.3-Flash NVFP4 · 4 × B200 PP4 · TraceLab coding-agent sessions · 目标来自 ServingStudio 模拟，实测来自 SSEngine

草稿 v3。写于 M6 eval 完成之后。
  • 最终对照（§5.6、§6.9–§6.10、§7）用 TraceLab v3（新模型）trace：20 分钟闭环用于真机对照，8 小时闭环只在 sim 里跑。
  • 引擎逐步搭建的 bring-up（§4–§6 中标“合成负载”或“旧 trace”的小节）用当时的合成负载和旧 trace，记录的是每一步的最终结果。
  • 真机数字来自 SSEngine（各节注明 Slurm 作业号）；sim 数字来自 ServingStudioSim 的 handoff glm53_flash_pp4_b200_v2 和之后的实验目录（v3 部分在 wt-pp-staged）。
  • 还没做完的工作集中在 §9。

上一份笔记用 ServingStudio 模拟器为 GLM-5.3-Flash 选出了一个方案：4 张 B200 组成 4 级 pipeline，scheduler 按最短剩余优先组 microbatch，session 的上下文保存在 HBM、DRAM 和 SSD 三层里。这份笔记记录把这个方案在真机上一步步实现出来的过程，回答两个问题：

  • 照着 sim 的设计做出来，能不能达到 sim 预测的性能？
  • 差距出在哪里？

Setting

  • 和上一份笔记相同：只做 prefill，decode 在别的 GPU 上。
  • 负载：20 分钟的闭环 coding-agent session，同时最多 N 个 session（N = 400 是 SLO 点，500 是过载点）。
  • SLO：p99 TTFT ≤ 6 s。

Method

  • 真机系统叫 SSEngine：自己写的小引擎（scheduler、KV/prefix cache、DRAM/SSD 分层、pipeline runtime、server）。
  • kernel 和模型层代码复用 vLLM 的 fork。
  • sim 给出每个阶段的目标（handoff），真机逐阶段追目标，一个阶段过关才进入下一个。

结论（概要）

  • 和 sim 对得上。HBM → DRAM → SSD 三层都打开时，真机和 sim 的吞吐在 N = 100 / 300 相差 1% 以内，N = 400 相差 4–5%。三档内存配置（full、Tiers、SSD-heavy）都是这样，命中在三层之间的分布也对得上（§6.9）。
  • 比 vLLM 快得多，TTFT 低一到两个数量级。同一 v3 负载、同样 4 张 B200，第 0–20 分钟：
    • N = 400：本引擎（Tiers）34.07 r/s，TTFT p50 / p90 / p99 0.99 / 4.70 / 61.00 s，超过 60 s 的 707 轮；vLLM DP4/EP4 6.58 r/s，36.23 / 67.53 / 201.68 s，910 轮；vLLM TP4 1.78 r/s，147.10 / 333.85 / 346.84 s，1,374 轮。吞吐分别是 5.2 倍和 19 倍。
    • N = 300：本引擎（full）32.03 r/s，0.23 / 0.99 / 19.83 s，205 轮；vLLM DP4/EP4 9.70 r/s，18.86 / 30.68 / 43.02 s，0 轮（吞吐 3.3 倍）；vLLM TP4 1.81 r/s，68.74 / 289.89 / 303.05 s，1,400 轮。
    • N = 100：三者都服务了所有到达的轮，但第 10–20 分钟 TTFT p50 / p90 / p99 本引擎 0.09 / 0.17 / 0.36 s，vLLM DP4/EP4 1.31 / 2.24 / 3.72 s，TP4 0.76 / 3.81 / 7.92 s（都没有超过 60 s 的轮）。见 §6.10。
  • 分层是吞吐的来源。N = 400 时三层让这 4 张 GPU 维持 37–41 r/s（第 10–20 分钟）；只用 HBM 时约 16 r/s（§5.6）。
  • 每一步 bring-up 都对上了目标。kernel、单层、单请求、所有请求在 t = 0 同时到达的饱和测试、prefix 命中、scheduler 的逐步检查、DRAM/SSD 读，都在目标的 ±10% 内或原因已知（§4–§6）。
  • sim 还决定了很多设计：DRAM 从 150 GB 降到 50 GB，SSD 只写 DRAM 淘汰的内容，SSD 定 128 GB，哪些优化不必做（§2）。
  • 容量不够会塌缩。没有 SSD 时命中会突然归零，每轮整段重算。sim 预测的塌缩窗口和真机相同，塌缩前逐窗口吻合；塌缩之后两边落到不同的稳态（§7）。
  • 剩下的差距有四个来源，都已定位：sim 不计写入代价；stage 2/3 的 GPU 更热、频率更低；KV block 取整浪费 HBM；主机开销（§8）。
  • 8 小时 sim 里带 SSD 的配置全程稳定。KDA state 只在少数位置可用，多存检查点、压缩 state 还没在真机上做（§7.5、§9）。

1背景与目标

要点
  • 45 层的 GLM-5.3-Flash 切成 4 级 pipeline，每级放整层，级内没有 TP/EP。
  • sim 把设计冻结成 handoff，分 7 个里程碑，每个都有目标数字和过关规则。
  • 每个里程碑先用合成 bring-up 负载过关，再上 session 负载。

1.1 模型与部署

  • 层：共 45 层，hidden size 4096。11 层是 DSA（sparse MLA + indexer，第 3、7、…、43 层），34 层是 KDA（linear attention）。
  • FFN：前 3 层是 dense FFN，其余 42 层是 MoE（288 个 routed expert，top-8）。
  • 精度：dense FFN 和 routed expert 用 NVFP4；attention、router、shared expert 和 lm_head 保持 BF16；KV cache 是 FP8。
  • 切分：4 级 pipeline，层的划分是 [12, 11, 11, 11]。级间传 4 路 residual stream，每 token 32 KiB。

  • DRAM 和 SSD 按 8,576 token 的 block 存；HBM 里的 KV 按 128 token 一页分配（取整的原因见 §8.2）。

1.2 负载

v3 trace（最终对照）

  • TraceLab v3：新模型下采集的 coding-agent session。真机对照用 20 分钟的版本（data/tracelab-v3/m6/sessions_2ps_v3.csv）。
  • 新 session 每秒到达 2 个，持续 20 分钟，共 2,457 个 session、26.1 万轮；同时最多 N 个活跃，多的排队等空位。每次运行从空 cache 开始。
  • 每一轮的 prompt = 上一轮的 prompt + 上一轮的输出 + 新 token。偶尔 agent 先截掉上下文的末尾，或者压缩上下文。
  • 平均每轮上下文约 16.9 万 token，新 token 2.7k，98% 是 session 自己的 prefix；最长的上下文接近 100 万 token。

1.3 sim 给出的设计与目标

  • sim 把设计冻结成一份 handoff（v2，ServingStudioSim 的 1de110c0）。
  • handoff 分 7 个文件，每个对应一个里程碑：约定、kernel、单层、单步迭代、prefix cache、scheduler、DRAM/SSD 分层。每个里程碑有自己的目标数字和过关规则。
  • 真机按 M1 到 M6 的顺序追。
  • 目标数字最初用默认 profile DB 生成；后来改用真实输入重新 profile kernel（realistic-input DB），真机对照的是后者，记作 v2-realistic（原因见 §4.7）。
  • 换成 v3 trace 之后，sim 目标在 wt-pp-staged 里按同样的设置重跑（logs/20261018_9_v3_m6 等，见 §11.2）。

1.4 “对齐”的含义

  • kernel、单层、单步迭代：每个 kernel 配置、每个 stage 的时间，和 profile 里的行或目标比，偏差在 ±10% 以内，否则要在 issues.md 里写出原因。
  • session：比较 rounds/s、新 token/s、TTFT p50 / p90 / p99、超过 60 s 的轮数。p99 落在“1% 的轮等满 60 s”这条边界附近，极其敏感，所以优先比较超过 60 s 的轮数和每分钟的 token 数。
  • 动态：每 2 分钟窗口的轮数、命中份额、各层读写次数。塌缩的配置只比较塌缩前的窗口。
  • 正确性：经过 cache 或分层读回后，输出 token 必须和不用 cache 时一致，分层读回的字节逐位相同。

3实现：SSEngine

要点
  • 引擎自己写，kernel 和模型层从 vLLM fork 当库导入，不复制任何 kernel。
  • 一个 controller 加 4 个 stage worker；级间激活走 copy engine，不占 SM。
  • 正确性的参照是 vLLM fork 的 TP4 + EP 单实例。

3.1 复用边界

  • kernel 和模型层复用 vLLM fork（892da0822f，vllm/models/glm5next），当作库导入。没有任何 kernel 被复制进 SSEngine。
  • 不运行 vLLM 的 engine、scheduler、model runner 或 KV manager。vLLM 只作为独立的正确性参照（§3.4）。

fork 有两处和 PP 不兼容，在 ssengine/model/pp_patch.py 里用小补丁覆盖：

  • mHC 的 stage 边界：fork 关掉了 glm5next 的 PP，stage 边界会丢掉 mHC 的延迟状态。发送方先做完最后一层的 hc_post，发完整的 4 路 residual；接收方第一层单独做 hc_pre。比目标里融合的 post+pre 每个边界慢 0.03 ms（8k）到 0.32 ms（128k），不到一个 stage 的 0.06%。
  • 只做 prefill，只出一个 token：没有 decode 路径，没有 MTP，stage 3 做 greedy 采样。

5Prefix cache 与 scheduler

要点
  • prefix 命中的 bring-up：40 个两轮 session 全部命中，第 1 轮 token 和不用 cache 时 40/40 相同。
  • scheduler 分 5 步搭建，每一步在“26 个请求同时到达”的检查里都和目标逐 microbatch 相同。
  • 只用 HBM 时，旧 trace 上 M5 的吞吐和 sim 相差 0–1.5%；v3 上 N = 300 已经放不下，要靠 DRAM 和 SSD。

5.1 Prefix cache

  • 每个 session 保留它最新的完整上下文：所有 DSA 层的 KV，加上最后一个 token 处的 KDA state。
  • KDA state 只在上下文末尾有效，所以命中规则是整段的：新 prompt 包含整段旧上下文就命中，否则从第一个 token 重算。
  • HBM 按 session 做 LRU 淘汰。

5.2 Prefix bring-up 合成负载

设置：40 个两轮 session，每个 (P, A) 组合 5 个。第 0 轮是 P token 的 prompt；第 1 轮在 10 s 后到达，带上第 0 轮的 prompt、输出 token 和 A − 1 个新 token。一次只有一个 session，GPU 都是空闲的。应该命中 P、只算 A。

  • 命中：40/40 命中 = P。
  • 过关（±10%）：8k + 1k、8k + 8k、32k + 8k、128k + 8k 每一列都过；32k + 1k 只有第 1 轮 TTFT 是 ×1.11。
  • 1k 追加随 P 变慢（×1.07 → 1.11 → 1.24 → 1.75，8k → 512k），而 stage 1–3 在 128k 以内都是 ×0.94–0.98：多出来的是每个请求的主机时间，随 prompt 长度增长（接收和解析 token id；512k 从到达到第一次下发约 27 ms），加上 stage 0 的 ×1.10–1.14。
  • 512k每个 stage ×1.07–1.33，第 0 轮 ×1.16；目标把 512k 的额外时间放在 indexer。后来在完整 pool 上测，512k 第 1 轮 HBM 命中仍比目标高 14%（65.79 对 57.5 ms，§6.8）。

正确性

  • cache 开 vs 关（7403）：40 个第 1 轮 prompt 全部命中，40/40 token 和不用 cache 时相同。
  • 不对齐的 P（P 不是 4 的倍数，7569）：命中 40/40，第 1 轮 token 38/40 相同；2 个不同都是近似平局（两边 top-2 是同一对 token，差 0–0.375 nats）。
  • 分块检查（7476、7569）：8,192 token 的分块和整段在 32,768 token 逐位相同；40,000 token 时 8,001 和 8,190 的分块（起点落在 indexer pool 中间、偏离 KDA 的 32-token 网格）在 split-K 噪声的 2 倍以内，KL 8e-6 / 1.5e-5，top-1 相同。
  • kpool GPU 测试：命中点在 P = 8193 + 1/2/3、各种分块方式下，indexer cache 的字节和不分块的 prefill 逐位相同。

6DRAM 与 SSD 分层

要点
  • 每个 block 按 1/4 分给 4 张 GPU 的 PCIe、DRAM 和 SSD，读写只用 copy engine。
  • bring-up：DRAM 读只增加读本身的时间；SSD 读在每个长度上达到目标；分层读回逐字节相同。
  • v3 三档 session：N = 100 / 300 吞吐和 sim 相差 1% 以内，N = 400 低 4–5%。
  • N = 300 / 400 时吞吐是 vLLM 的 3–19 倍；各 N 下 TTFT 都低约一到两个数量级。

6.1 设计：balanced storage 与两跳

  • 按 1/4 分摊：每个 block 的每一段字节按 1/4 分给 4 张 GPU，GPU q 负责第 q 份的 PCIe、主机内存和 SSD 文件。数据离开 GPU 前先用 NVLink 汇集好，所以 4 条 PCIe 链路的负载严格相等：每 token 1,499 B，一个 block 每张 GPU 36.9 MB。
  • 不分摊的代价：如果每个 stage 只存自己的字节，stage 0、2、3 的链路比平均多 9%，stage 1 少 27%，最慢的链路决定读完的时间。
  • 两跳：读的时候，GPU q 用自己的 PCIe 把第 q 份 H2D 拷进自己 HBM 的 staging ring，再用 cuMemcpyBatchAsync 走 NVLink 把各层送到对应的 stage。写的时候方向相反。
  • 只用 copy engine：不占 SM。stage 在满载时 SM 全忙，GEMM 8192³ 单独 0.682 ms，4 张 GPU 同时 H2D 时 0.677 ms。
  • 不做逐层流水：一轮在它的 prefix 全部读完后才开始算。DRAM 读 1.7–16 ms，SSD 读 9–82 ms，首轮计算 52–57 ms。
  • 读等待上限：一个读要等超过 1 s 才能开始，这一轮就先跳过，留在队列里。

6.3 主机内存安全

full 档原来每张 GPU 固定 150 GB DRAM，4 张共 600 GB，必须落在 GPU 所在的 NUMA node 上。这台机器每个 node 约 1,057 GB，和别人共用，node 0 上还有一台最多 512 GiB 的虚拟机。最终的做法：

  • 每 1 GiB 先检查该 node 的空闲内存加可回收的干净 page cache，够才把这一块 bind 到该 node 再 touch；不够就报错，不溢出到另一个 node。
  • 启动前按 node 预检（arena 加 115 GB 余量），运行中按 node 盯着空闲内存、PSI 和 D 状态进程，越线就停掉自己的运行。
  • 进程的 oom_score_adj 设为 1000，真到 OOM 时先杀自己。
  • 8043 上验证：4 × 150 GB 全部落在 node 1，page cache 从 665 GB 回收到 339 GB，touch 41–43 s。

6.4 KV pool 的五层结构

分层存储重构成 ssengine/kvpool 下的五层：

  • layout：字节范围。
  • placement：balanced 的 1/4 规则。
  • backends：DRAM arena、SSD 文件。
  • mover：两跳拷贝。
  • manager：纯策略：索引、LRU、slot、写回。

scheduler 只看 lookup / load / store 这几个接口。重构前后 full 档 N = 400 每分钟处理量相差 1% 以内（下图，旧 trace）。

6.5 写入策略的演进

handoff 原来的写法是写透：每轮结束，上下文同时写进 DRAM 和 SSD。sim 里做了两步改动：

  • DRAM 改成 victim：只写 HBM 淘汰的内容。DRAM 不再重复存 HBM 已有的东西，full 档 DRAM 50 GB 就和写透的 150 GB 一样。
  • SSD 改成 DRAM 的 victim：只写 DRAM 淘汰的内容，增量写，读回后保留干净副本。
  • 合起来是 HBM → DRAM → SSD 的逐级写回。真机上，每一级都在占用超过水位线时提前把 LRU 尾部写到下一级，淘汰时一般不用等写完。
  • 两级用同一个写回类，scheduler 不知道底下是哪种写法。
  • 写进 SSD 的数据有 68–82% 后来被读回（Tiers、SSD-heavy）。
  • 最大的浪费是 session 已经结束才下沉的内容，占 9–17%；full 档几乎全是这种，但量本身很小。

7.2 机制

原因在 scheduler，不在淘汰策略。两个量：

  • W(t)：闭环在 t 时刻需要保留的上下文。每个还有下一轮、而下一轮还没被服务的 session，它最近一轮的 prompt，加上 KDA 末尾 state（约合 24,600 token）。
  • C：HBM 加 DRAM 的容量。
  • 丢失翻倍：W 超过 C 后，丢失上下文的轮每个窗口翻一倍左右（h25d50：12 → 43 → 102 → 131）。每次丢失是一次约 11 万 token 的整段重算，等满 60 s 后被强制准入。
  • 自我强化：强制调度按等待时间从老到新，所以每一轮都要排在这些重算后面。重算让排队更长，排队又让更多上下文在 cache 里待不住。这是一个 metastable 循环。
  • v3 的 W 更大：N = 400 时 W 在第 4 分钟到 3,300 万，第 8–20 分钟到 5,200–6,500 万，比旧 trace 多，涨得也快。
  • C 越大塌得越晚：扫描里 C ≤ 5,700 万的 N = 400 配置都在 20 分钟内塌缩，比 W 第一次超过 C 晚 1–3 个窗口。C = 4,100 万在第 6–8 分钟，4,860 万在第 12–14 分钟，5,700 万在第 18–20 分钟（命中份额第一次低于 0.5 的窗口）。
  • W 超过 C 不一定马上塌：h20d75（C = 6,230 万）从第 14 分钟起 W 比 C 多出最多 260 万，仍然撑住；h25d37 在 N = 300 时按原速稳定，GPU 时间放慢 3% 就在第 16–18 分钟塌缩。靠近边缘时，小的速度差就决定塌不塌。

结论：

  • 只靠 DRAM 时，N = 400 需要 C 大约等于 W 的峰值，约 6,500 万 token，也就是每 GPU 25 GB HBM 加 75 GB DRAM。
  • 旧的 h25d37、h12d19 设置，以及 eval 的 20/20、12.5/12.5 两档，去掉 SSD 后在 v3 上都在第 4–8 分钟塌缩。
  • 带 SSD 128 GB 时三档都不塌（§6.9）。

8sim 有多准

要点
  • 从 kernel 到 20 分钟闭环 session，误差没有层层放大：吞吐 1–5%，命中分布和塌缩窗口都对得上。
  • 偏差有六个，原因都已找到；只有塌缩之后 sim 的读启动规则还没在代码里确认。

8.1 吻合的部分

  • kernel、单步迭代、bring-up：kernel 中位比值 0.95–1.08；单请求和同时到达的饱和测试都在 ±10% 以内；调度检查逐 microbatch 相同；DRAM、SSD 读时间达到目标（§4–§6.8）。
  • 吞吐：旧 trace 只用 HBM（M5）相差 0–1.5%；v3 三档分层，N = 100 / 300 时 rounds/s 相差 1% 以内，N = 400 低 4–5%；命中在 HBM、DRAM、SSD 之间的分布对得上。
  • 长尾：N = 400 的 p99 落在 60 s 强制调度的边界上，超过 60 s 的轮 1.02% 对 0.77%。
  • 动态：只有 DRAM 时，塌缩前每 2 分钟的轮数、命中份额、丢失的轮、重算量和 W 逐窗口吻合，塌缩出现在同一个窗口（旧 trace 和 v3 都是）；边缘配置两边都稳定。只用 HBM、N = 400 的双稳态区，真机落在 sim 扰动范围的中位数上。

场景本身很复杂：20 分钟闭环、上下文接近 100 万 token、4 级 pipeline、session 级 prefix cache、三层分层读回、SRPT、读等待上限、装载区、60 s 强制规则叠在一起，误差却没有层层放大。

写入代价

  • 现象：不留装载区（excl）时，sim 和 st10 一样（N = 400 Tiers 39.79 对 39.77 r/s），真机却低 12%（33.10 对 37.66；8453 对 8431）。N = 300 时吞吐低 1.7%，TTFT p90 0.80 s 对 0.42 s，重算 / 新 token 0.094 对 0.025。
  • 机制：一个等待环。没有装载区，读落地要等淘汰写入腾出 block，而这些写入又在等在途读占着的 DRAM slot。DRAM 读 p50 因此是 217 ms（st10 55 ms），stage 0 忙碌率降到 0.875。
  • sim 看不到：它不计写入时间。所以装载区是必需的。
  • 同一类差距：SSD bring-up 里 512k 多出的 50 ms（§6.8）、只有 DRAM 的 h25d75 真机低 12.6%（§7.1）。

热卡

  • 两组 4 张 GPU 里，第 3、4 张卡（stage 2、3）都比前两张热 10–14 °C，在 1000 W 的功耗上限下频率低 5–7%。
  • stage 2/3 本来就是 pipeline 里最忙的（忙碌率 94–98%），按每千 token 的毫秒数比 sim 慢约 7%。把 GPU 顺序反过来跑，一部分差距跟着 GPU 走。
  • 同频率下每个 op 的真机 / sim 比值在 4 个 stage 上相同，所以这不是 profile 或代价模型的问题。
  • sim 整体放慢 3%（gpu_time_multiplier 1.025–1.035）能复现 N = 400 差距的约 2/3（41.1 r/s，TTFT 0.56 / 1.44 / 54 s）；N = 300 的损失集中在 stage 2/3 接近饱和的时候，整体放慢解释不了多少。N = 300 小请求多出的约 30 ms 也是这个原因。
  • 不给 sim 加逐 stage 的系数：那等于给 GPU 插槽的位置建模。

block 取整

  • HBM 原来按 8,576 token 的 block 分配，每个上下文平均浪费 4.3k token，约 2.4% 的 HBM。
  • 只用 HBM、N = 400 正好在容量边缘，这 2.4% 就决定了结果：sim 把容量减 2.4% 后给出 11.2–12.7 r/s、重算 / 新 token 约 1.75，和 block 版的真机（12.97 r/s、1.76）一致。
  • HBM 改成 128 token 一页后，每个上下文只浪费 63 token，真机 16.16 r/s、重算 / 新 token 1.21，落在 sim 满容量的中位数上（§5.6）。

  • sim：第 12 分钟后到达的 601 轮中，569 轮到达时上下文还在 DRAM，但到出第一个 token 时一个都不在了：上下文在到达后 163 / 183 / 189 s 被 LRU 淘汰，期间没有开始读。
  • 推测：sim 的分阶段装载在逾期队列前面还有整段重算时，不会启动逾期轮的 DRAM 读。还没在代码里确认（wt-pp-staged 的 fresh_source.rs 中 FreshQueues::stage_loads，prefix_fetch.rs 中 PrefixFetch::stage / load_gate）。

  • prompt 停在上一轮 prompt 中间（inside_prompt）：7.3 / 8.0 / 10.7%。prompt 真的比上一轮短（截断或压缩）。k2 之后剩下的都是这一类；k4 和 anchor 拿回其中一部分。
  • 其余的轮：0.04%。

取舍。

  • k2 性价比最高。只多存一个 state，多存的 state 在 DRAM + SSD 上约 0.58 TB，就把多算从 13–25% 降到 7–10%，r/s 提高 6 / 10 / 14%。state 写入从约 2.5 GB/s 涨到 5.4–5.6 GB/s，离带宽还远。
  • k4 只再多 1.7–1.8%。它把多算再减半，但在不留装载区的 base 模式下反而比 k2 慢：每次读要搬 4 个 state，SSD 读到 9.3–9.7 GB/s，接近 10 GB/s 的通道。
  • anchor 比 k2 多 2–4%。m1s2 拿回离线上限（任意位置都能接着算）收益的 44–51%，m2s2 拿回 64–73%。代价在 I/O：多存的 state 涨到 1.2 TB（m1s2）和 1.7–1.8 TB（m2s2），state 写入涨到 8.0 和 9.5–9.9 GB/s，SSD 读 8.1–9.1 GB/s；m2s2 在 c1563 / c2000 的计算量降到 137.6–138.4k token/s，开始受 I/O 限制。m3s2 不比 m2s2 好。
  • anchor 原地保留更划算。让 anchor 留在它第一次落入的那一层，不再随条目逐级降级（e4de4292）：m2s2 的 state 写入回到 5.9–6.0 GB/s，和 k2 同一水平，r/s 比 k2 高 4.1 / 5.7 / 7.7%。
  • 20 分钟 eval 用不上。M6 v3 trace 在没有 cache 压力时，k1 多算 1.57%，k2 1.18%，k4 0.88%；m1s2 只省 k1 计算量的 0.46%。所以 §6.9 的对照不受 k 影响，k 只在长 session、长时间运行时重要。

计划：真机先做 k2（原子条目、按真实字节计费、读只搬存活的 state）。anchor 要和 §9.2 的压缩或原地保留一起做，否则多出来的 state 写入会吃掉收益。

9.2 分层里的 KDA state 压缩

KDA state 每层是 fp32 的 [H, 128, 128]。写进 DRAM 和 SSD 时按一条阈值规则压缩：|x| < 0.3 的值存成 fp16(x · 216)（2 的幂缩放，缩放本身无误差），其余保留 fp32。

  • 压缩比和误差。在从 SSEngine SSD shard 里取出的 19 个真实 state 上：压缩比约 1.86×，相对 RMS 误差 1.8e-7，最大的 1% 的值无损。大部分 head 的 max|x| < 0.3，整个 head 可以存成定长的 fp16。
  • 对照：无损压缩（zstd 加 byte shuffle）只有约 1.15×；同样大小的 bf16 误差大 8 倍；不缩放的 fp16 会把约 22% 的值变成零或非规格化数。
  • 误差不会累积。KDA 的更新对 state 误差是非扩张的（k 是单位向量，β、α ∈ (0, 1)），压缩误差在接着算时不会放大。CPU 上接着算的检查显示，误差比 bf16 输入本身的噪声小 10 倍以上。
  • 编解码只在主机 CPU 上做。满载时 stage 的 SM 全忙，分层路径只用 copy engine（§6.1），所以不用 GPU 编解码。HBM 里的 state 不压缩。

10结论与下一步

  • 范围：这个模型和硬件、v3 负载、HBM → DRAM → SSD 三层、不塌缩的配置。
  • 准确度：sim 对吞吐的预测误差在 1–5%，命中在三层间的分布和塌缩的窗口也对得上；每一步 bring-up（kernel、单请求、同时到达、prefix、调度检查、分层读）都和目标对上。
  • 差距都找到了原因：写入代价、热卡、block 取整、主机开销。
  • 比 vLLM 好：同一负载下 N = 400、第 0–20 分钟，吞吐是 vLLM DP4/EP4 的 5.2 倍、TP4 的 19 倍；TTFT p50 / p90 / p99 0.99 / 4.70 / 61.00 s 对 36.23 / 67.53 / 201.68 s（DP4/EP4）和 147.10 / 333.85 / 346.84 s（TP4）。
  • 更重要的是，sim 让我们在动手之前算清了 DRAM、SSD 的大小和写法、装载区的大小，以及哪些优化不必做。
