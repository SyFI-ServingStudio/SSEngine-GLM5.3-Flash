From sim to real engine: implementing and aligning GLM-5.3-Flash NVFP4 PP4 on B200

GLM-5.3-Flash NVFP4 · 4 × B200 PP4 · TraceLab coding-agent sessions · targets from the ServingStudio sim, measurements from SSEngine

Draft v3. Written after the M6 eval completed.
  • The final comparison (§5.6, §6.9–§6.10, §7) uses the TraceLab v3 (new model) trace: the 20-minute closed loop is used for the real-engine comparison, the 8-hour closed loop only runs in sim.
  • The engine bring-up step by step (sections marked "synthetic load" or "old trace" in §4–§6) used the synthetic load and old trace of that time; what is recorded is the final result of each step.
  • Real-engine numbers come from SSEngine (each section notes the Slurm job id); sim numbers come from the ServingStudioSim handoff glm53_flash_pp4_b200_v2 and the experiment directories after it (the v3 part is in wt-pp-staged).
  • Unfinished work is collected in §9.

The previous note used the ServingStudio simulator to pick a design for GLM-5.3-Flash: 4 B200s in a 4-stage pipeline, a scheduler that groups microbatches by shortest remaining first, and session context kept in three tiers: HBM, DRAM and SSD. This note records the process of implementing that design step by step on the real engine and answers two questions:

  • If we build it following the sim design, do we reach the performance the sim predicted?
  • Where does the gap come from?

Setting

  • Same as the previous note: prefill only, decode runs on other GPUs.
  • Load: 20-minute closed-loop coding-agent sessions, at most N concurrent sessions (N = 400 is the SLO point, 500 is the overload point).
  • SLO: p99 TTFT ≤ 6 s.

Method

  • The real engine is called SSEngine: a small engine we wrote ourselves (scheduler, KV/prefix cache, DRAM/SSD tiering, pipeline runtime, server).
  • Kernel and model layer code reuse a vLLM fork.
  • The sim gives the target for each stage (handoff); the real engine chases the target stage by stage, and only moves to the next stage once one stage passes.

Conclusions (summary)

  • It matches the sim. With all three tiers HBM → DRAM → SSD enabled, real-engine and sim throughput differ by less than 1% at N = 100 / 300 and by 4–5% at N = 400. This holds for all three memory settings (full, Tiers, SSD-heavy), and the distribution of hits across the three tiers also matches (§6.9).
  • Much faster than vLLM, with TTFT one to two orders of magnitude lower. Same v3 load, same 4 B200s, minutes 0–20:
    • N = 400: this engine (Tiers) 34.07 r/s, TTFT p50 / p90 / p99 0.99 / 4.70 / 61.00 s, 707 rounds over 60 s; vLLM DP4/EP4 6.58 r/s, 36.23 / 67.53 / 201.68 s, 910 rounds; vLLM TP4 1.78 r/s, 147.10 / 333.85 / 346.84 s, 1,374 rounds. Throughput is 5.2x and 19x respectively.
    • N = 300: this engine (full) 32.03 r/s, 0.23 / 0.99 / 19.83 s, 205 rounds; vLLM DP4/EP4 9.70 r/s, 18.86 / 30.68 / 43.02 s, 0 rounds (3.3x throughput); vLLM TP4 1.81 r/s, 68.74 / 289.89 / 303.05 s, 1,400 rounds.
    • N = 100: all three served every arriving round, but for minutes 10–20 TTFT p50 / p90 / p99 is 0.09 / 0.17 / 0.36 s for this engine, 1.31 / 2.24 / 3.72 s for vLLM DP4/EP4, and 0.76 / 3.81 / 7.92 s for TP4 (none had rounds over 60 s). See §6.10.
  • Tiering is where the throughput comes from. At N = 400 the three tiers keep these 4 GPUs at 37–41 r/s (minutes 10–20); with HBM only it is about 16 r/s (§5.6).
  • Every bring-up step met its target. Kernel, single layer, single request, the saturation test with all requests arriving at once at t = 0, prefix hits, the scheduler's step-by-step checks, and DRAM/SSD reads are all within ±10% of target or have a known cause (§4–§6).
  • The sim also decided many design points: DRAM cut from 150 GB to 50 GB, SSD writes only what DRAM evicts, SSD sized at 128 GB, and which optimizations are not worth doing (§2).
  • Insufficient capacity causes collapse. Without SSD, hits suddenly drop to zero and every round recomputes the whole context. The collapse window predicted by the sim matches the real engine, and the per-window match holds before collapse; after collapse the two settle into different steady states (§7).
  • The remaining gap has four sources, all located: the sim does not count write cost; GPUs on stage 2/3 run hotter and at lower clocks; KV block rounding wastes HBM; host overhead (§8).
  • In the 8-hour sim the configuration with SSD is stable throughout. KDA state is only usable at a few positions; storing more checkpoints and compressing state have not been done on the real engine yet (§7.5, §9).

1Background and targets

Key points
  • The 45-layer GLM-5.3-Flash is cut into a 4-stage pipeline, each stage holds whole layers, no TP/EP within a stage.
  • The sim freezes the design into a handoff, split into 7 milestones, each with target numbers and pass rules.
  • Each milestone first passes with a synthetic bring-up load, then moves on to the session load.

1.1 Model and deployment

  • Layers: 45 layers in total, hidden size 4096. 11 layers are DSA (sparse MLA + indexer, layers 3, 7, …, 43), 34 layers are KDA (linear attention).
  • FFN: the first 3 layers are dense FFN, the remaining 42 layers are MoE (288 routed experts, top-8).
  • Precision: dense FFN and routed experts use NVFP4; attention, router, shared expert and lm_head stay BF16; KV cache is FP8.
  • Partitioning: 4-stage pipeline, layer split is [12, 11, 11, 11]. 4 residual streams are passed between stages, 32 KiB per token.

  • DRAM and SSD store in blocks of 8,576 tokens; KV in HBM is allocated in pages of 128 tokens (the reason for the rounding is in §8.2).

1.2 Load

v3 trace (final comparison)

  • TraceLab v3: coding-agent sessions collected under the new model. The real-engine comparison uses the 20-minute version (data/tracelab-v3/m6/sessions_2ps_v3.csv).
  • New sessions arrive at 2 per second for 20 minutes, 2,457 sessions in total, 261k rounds; at most N are active at once, the rest queue for a slot. Each run starts from an empty cache.
  • The prompt of each round = the previous round's prompt + the previous round's output + new tokens. Occasionally the agent first truncates the end of the context, or compresses the context.
  • The average context per round is about 169k tokens, new tokens 2.7k, 98% is the session's own prefix; the longest context is close to 1M tokens.
  • These 4 GPUs only count the prefill plus the first output token of each round. The next round arrives after the decode time (80 token/s) plus the tool wait.
  • The hour-scale steady state only runs in sim: 8-hour closed loop, with 1,563 / 2,000 / 2,500 concurrent sessions (data/tracelab-v3/traces/closed_c*_s0.csv), see §7.5.

1.3 Design and targets given by the sim

  • The sim freezes the design into a handoff (v2, 1de110c0 of ServingStudioSim).
  • The handoff has 7 files, one per milestone: conventions, kernel, single layer, single-step iteration, prefix cache, scheduler, DRAM/SSD tiering. Each milestone has its own target numbers and pass rules.
  • The real engine follows in order from M1 to M6.
  • The target numbers were initially generated with the default profile DB; later the kernels were re-profiled with real inputs (realistic-input DB), and the real engine is compared against the latter, denoted v2-realistic (reason in §4.7).
  • After switching to the v3 trace, the sim targets were re-run in wt-pp-staged with the same settings (logs/20261018_9_v3_m6 etc., see §11.2).

1.4 What "aligned" means

  • kernel, single layer, single-step iteration: for each kernel configuration and each stage's time, the deviation from the row in the profile or from the target is within ±10%, otherwise the reason must be written in issues.md.
  • session: compare rounds/s, new tokens/s, TTFT p50 / p90 / p99, and the number of rounds exceeding 60 s. p99 sits near the boundary of "1% of rounds wait the full 60 s" and is extremely sensitive, so the number of rounds exceeding 60 s and the tokens per minute are compared first.
  • dynamics: rounds per 2-minute window, hit share, read/write counts per tier. For a collapsed configuration, only the windows before the collapse are compared.
  • correctness: after reading back through cache or tiering, the output tokens must match those without cache, and the bytes read back through tiering must be bit-identical.

3Implementation: SSEngine

Key points
  • The engine is written in-house; kernels and model layers are imported as a library from the vLLM fork, and no kernel is copied.
  • One controller plus 4 stage workers; inter-stage activations go over the copy engine and do not use SMs.
  • The correctness reference is the vLLM fork's TP4 + EP single instance.

3.1 Reuse boundary

  • Kernels and model layers reuse the vLLM fork (892da0822f, vllm/models/glm5next), imported as a library. No kernel is copied into SSEngine.
  • vLLM's engine, scheduler, model runner, or KV manager are not run. vLLM serves only as an independent correctness reference (§3.4).

The fork has two PP incompatibilities, overridden with small patches in ssengine/model/pp_patch.py:

  • mHC stage boundary: the fork disables PP for glm5next, and the stage boundary would lose mHC's delay state. The sender first finishes the last layer's hc_post and sends the full 4-way residual; the receiver does hc_pre separately in its first layer. This is 0.03 ms (8k) to 0.32 ms (128k) slower per boundary than the fused post+pre in the target, under 0.06% of a stage.
  • Prefill only, one token out: no decode path, no MTP, stage 3 does greedy sampling.

5Prefix cache and scheduler

Key points
  • Prefix-hit bring-up: all 40 two-round sessions hit, and round 1 tokens match 40/40 with the no-cache run.
  • The scheduler was built in 5 steps, and every step matches the target microbatch by microbatch in the "26 requests arrive at once" check.
  • With HBM only, M5 throughput on the old trace is within 0–1.5% of the sim; on v3, N = 300 no longer fits and needs DRAM and SSD.

5.1 Prefix cache

  • Each session keeps its latest full context: the KV of all DSA layers, plus the KDA state at the last token.
  • The KDA state is only valid at the end of the context, so the hit rule is whole-segment: if the new prompt contains the entire old context it hits, otherwise it recomputes from the first token.
  • HBM evicts by session with LRU.

5.7 What went wrong

  • Low-load TTFT is high: on v3 at N = 100, TTFT p50 is 0.09 s in the real engine and 0.08 s in sim.   • Power cap: under full load the B200 sits at a power cap of about 1000 W. Optimizations that only shorten time, like removing launch gaps or copies, just lower the clock and leave throughput unchanged; only fewer bytes or FLOPs help. Recorded only.
  • Two sim rules the real engine cannot do: in the trace, 4,933 rounds retain only the previous round's partial context (rewind); sim releases the slot as soon as the session's last round emits a token. Both affect the design run by less than 1%.

6DRAM and SSD tiering

Key points
  • Each block is split 1/4 across the 4 GPUs' PCIe, DRAM and SSD, and reads and writes use only copy engines.
  • Bring-up: a DRAM read adds only the read time itself; SSD reads meet target at every length; tiered read-back is byte-for-byte identical.
  • v3 three-setting sessions: throughput is within 1% of sim at N = 100 / 300 and 4–5% lower at N = 400.
  • At N = 300 / 400 throughput is 3–19x vLLM; TTFT is about one to two orders of magnitude lower at every N.

6.1 Design: balanced storage and two hops

  • Split by 1/4: every byte range of every block is split 1/4 across the 4 GPUs, and GPU q owns the PCIe, host memory and SSD files for share q. Data is gathered over NVLink before leaving the GPU, so the 4 PCIe links carry exactly equal load: 1,499 B per token, 36.9 MB per GPU per block.
  • Cost of not splitting: if each stage stored only its own bytes, the stage 0, 2 and 3 links would carry 9% above average and stage 1 27% below, and the slowest link determines read completion time.
  • Two hops: on a read, GPU q copies share q H2D over its own PCIe into a staging ring in its own HBM, then uses cuMemcpyBatchAsync over NVLink to send each layer to the corresponding stage. Writes go the other way.
  • Copy engines only: no SMs used. At full load the stage has all SMs busy: GEMM 8192³ alone takes 0.682 ms, and 0.677 ms with 4 GPUs doing H2D at the same time.
  • No per-layer pipelining: a round starts computing only after its entire prefix is read. DRAM reads take 1.7–16 ms, SSD reads 9–82 ms, first-round compute 52–57 ms.
  • Read wait limit: if a read would have to wait more than 1 s to start, the round is skipped for now and left in the queue.

6.3 Host memory safety

The full setting originally pinned 150 GB DRAM per GPU, 600 GB across 4 GPUs, and it must land on the NUMA node where the GPU sits. The node has about 1,057 GB per node and is shared with others; node 0 also hosts a VM of up to 512 GiB. The final approach:

  • For each 1 GiB, first check the node's free memory plus reclaimable clean page cache; only if it is enough, bind that block to the node and then touch it; if not, raise an error and do not spill over to the other node.
  • Pre-check per node before start (arena plus 115 GB headroom); at runtime, watch free memory, PSI and D-state processes per node, and stop our own run when a threshold is crossed.
  • Set the process's oom_score_adj to 1000, so that on a real OOM it kills itself first.
  • Verified on 8043: all 4 × 150 GB landed on node 1, page cache was reclaimed from 665 GB down to 339 GB, touch took 41–43 s.

6.4 The five-layer KV pool structure

Tiered storage was restructured into five layers under ssengine/kvpool:

  • layout: byte ranges.
  • placement: the balanced 1/4 rule.
  • backends: DRAM arena, SSD files.
  • mover: two-hop copy.
  • manager: pure policy: index, LRU, slot, writeback.

The scheduler only sees the lookup / load / store interfaces. Before and after the refactor, the full setting at N = 400 differs by less than 1% in per-minute throughput (figure below, old trace).

6.5 Evolution of the write policy

handoff originally used write-through: at the end of every round, the context was written to both DRAM and SSD. Two changes were made in the sim:

  • DRAM becomes a victim: only write what HBM evicts. DRAM no longer duplicates what HBM already holds, so the full setting's 50 GB DRAM behaves like 150 GB of write-through.
  • SSD becomes DRAM's victim: only write what DRAM evicts, as incremental writes, keeping a clean copy after reading back.
  • Together this is staged writeback HBM → DRAM → SSD. In the real engine, each level proactively writes the LRU tail to the next level when its occupancy exceeds the watermark, so eviction generally does not wait for the write to finish.
  • Both levels use the same writeback class; the scheduler does not know which variant is underneath.
  • 68–82% of the data written to SSD is later read back (Tiers, SSD-heavy).
  • The biggest waste is content demoted after its session has already ended, accounting for 9–17%; in the full setting it is almost all of this kind, but the volume itself is small.

6.6 SSD I/O

  • One io_uring per GPU: O_DIRECT, DRAM arena and staging registered as fixed buffers, one slot per request (12.86 MB), reads prioritized over writeback, a single thread handles submission and completion.
  • If the ring cannot be created, it errors out immediately; there is no fallback to the thread approach.

6.12 What went wrong

  • 7996, global OOM (10-18 00:43): full setting N = 500 used a strict NUMA bind, exhausted node 0, and the kernel's OOM killer killed other users' processes. Rule since then: preventing host OOM is the top priority, no more blind strict binds.
  • 7976, host memory blown up: another user's job on the same machine plus a VM took a large amount of memory, PSI full reached 64%, some workers entered D state, and the run was voided. MADV_HUGEPAGE makes touch do memory compaction synchronously, so 150 GB took about 500 s; switched back to 4 KiB pages (7991 measured the same read bandwidth for 4 KiB and 2 MiB).
  • 8036, did not start: the precheck found node 0 was insufficient. Another job's GPUs were on 4–7 but almost all its memory was on node 0: the cluster's Slurm does not align CPU and GPU by node (gres.conf has no Cores=), and memory follows the CPU. Since then DRAM-heavy runs are pinned to GPU 4–7.
  • 8039, spilled to another node: the precheck counted page cache as available, but MPOL_PREFERRED with zone_reclaim_mode 0 does not reclaim page cache and allocates directly on another node instead, so 365 GB of the 600 GB landed on node 0. Changed to "check chunk by chunk, then bind" (§6.3).
  • 8042, 32k TTFT 4.4 ms higher: reads and dispatch 1.8 ms higher, stage 0/1 compute about 1 ms higher each, stage 2/3 unchanged. Host load was 245 at the time (6.5 at 7966); the slowness was in the host dispatching kernels, not a problem with the refactor.
  • SSD I/O replaced the thread approach: 8-thread preadv reaches the bandwidth, but CPU and tail latency are both twice io_uring's (§6.6).
  • Write-through design was replaced: the earliest design wrote through on handoff, DRAM 150 GB and SSD every round. It met the target (7995, 8043), but host memory and SSD writes both far exceeded what was needed.

7Instability and collapse

Key points
  • Without SSD and with insufficient capacity, the system collapses: hits suddenly drop to zero, the full segment is recomputed every round, and it never recovers.
  • The predicted quantities are the retained context W and the capacity C: once W exceeds C, collapse follows within 1–3 windows. sim and the real engine collapse in the same window.
  • The remedy is capacity: configurations with SSD are stable in both the 20-minute real run and the 8-hour sim.

7.2 Mechanism

The cause is in the scheduler, not in the eviction policy. Two quantities:

  • W(t): the context the closed-loop must retain at time t. For every session that still has a next round and whose next round has not been served yet, its most recent round's prompt plus the KDA tail state (about 24,600 token).
  • C: the capacity of HBM plus DRAM.
  • Losses double: after W exceeds C, rounds that lose their context roughly double every window (h25d50: 12 → 43 → 102 → 131). Each loss is a full-segment recompute of about 110K token, which is force-admitted after waiting the full 60 s.
  • Self-reinforcing: forced scheduling goes from oldest to newest by wait time, so every round has to queue behind these recomputes. Recompute makes the queue longer, and the longer queue makes more contexts unable to stay in cache. This is a metastable loop.
  • v3 has a larger W: at N = 400, W reaches 33M at minute 4 and 52–65M in minutes 8–20, more than the old trace and rising faster.
  • Larger C collapses later: in the sweep, all N = 400 configurations with C ≤ 57M collapse within 20 minutes, 1–3 windows after W first exceeds C. C = 41M at minutes 6–8, 48.6M at minutes 12–14, 57M at minutes 18–20 (the window where hit share first drops below 0.5).
  • W exceeding C does not always collapse immediately: h20d75 (C = 62.3M) has W exceeding C by up to 2.6M from minute 14 onward and still holds; h25d37 is stable at N = 300 at the original speed, and collapses at minutes 16–18 when GPU time is slowed by 3%. Near the edge, a small speed difference decides whether it collapses.

Conclusions:

  • With DRAM only, N = 400 needs C roughly equal to the peak of W, about 65M token, that is 25 GB HBM plus 75 GB DRAM per GPU.
  • The old h25d37 and h12d19 settings, and the eval's 20/20 and 12.5/12.5 settings, all collapse at minutes 4–8 on v3 once SSD is removed.
  • With SSD 128 GB none of the three settings collapses (§6.9).

8How accurate is sim

Key points
  • From kernel to 20-minute closed-loop session, errors did not amplify layer by layer: throughput 1–5%, hit distribution and collapse window both match.
  • There are six deviations, and all causes have been found; only sim's read-start rule after collapse has not yet been confirmed in code.

8.1 Where it matches

  • kernel, single-step iteration, bring-up: kernel median ratio 0.95–1.08; single-request and simultaneous-arrival saturation tests are within ±10%; scheduling checks are identical per microbatch; DRAM and SSD read times meet target (§4–§6.8).
  • Throughput: old trace with HBM only (M5) differs by 0–1.5%; v3 three-tier, at N = 100 / 300 rounds/s are within 1%, at N = 400 4–5% lower; hit distribution among HBM, DRAM, and SSD matches.
  • Tail: p99 at N = 400 falls on the boundary of 60 s forced scheduling; rounds over 60 s are 1.02% vs 0.77%.
  • Dynamics: with DRAM only, before collapse the number of rounds per 2 minutes, hit share, lost rounds, recompute amount, and W match window by window; collapse appears in the same window (both old trace and v3); edge configurations are stable on both sides. In the HBM-only, N = 400 bistable region, the real engine falls on the median of sim's perturbation range.

The scenario itself is complex: 20-minute closed loop, context approaching 1M tokens, 4-stage pipeline, session-level prefix cache, three-tier read-back, SRPT, read wait cap, loading area, and the 60 s forced rule all stacked together, yet errors did not amplify layer by layer.

Write cost

  • Phenomenon: With no loading area (excl), sim is the same as st10 (N = 400 Tiers 39.79 vs 39.77 r/s), but the real engine is 12% lower (33.10 vs 37.66; 8453 vs 8431). At N = 300 throughput is 1.7% lower, TTFT p90 0.80 s vs 0.42 s, recompute / new token 0.094 vs 0.025.
  • Mechanism: A wait loop. With no loading area, read placement must wait for eviction writes to free blocks, and these writes wait for DRAM slots occupied by in-flight reads. DRAM read p50 is therefore 217 ms (st10 55 ms), and stage 0 busy rate drops to 0.875.
  • What sim cannot see: it does not account for write time. So the loading area is necessary.
  • Same class of gap: the extra 50 ms for 512k in SSD bring-up (§6.8), the DRAM-only h25d75 real engine 12.6% lower (§7.1).

Hot cards

  • Across the two groups of 4 GPUs, cards 3 and 4 (stage 2, 3) run 10–14 °C hotter than the first two and clock 5–7% lower under the 1000 W power cap.
  • stage 2/3 are already the busiest in the pipeline (busy rate 94–98%), running about 7% slower than sim in ms per thousand tokens. Running the GPUs in reverse order moves part of the gap with the GPU.
  • At the same clock, the real engine / sim ratio per op is identical across the 4 stages, so this is not a profile or cost-model issue.
  • Slowing sim down by 3% overall (gpu_time_multiplier 1.025–1.035) reproduces about 2/3 of the N = 400 gap (41.1 r/s, TTFT 0.56 / 1.44 / 54 s); the N = 300 loss is concentrated when stage 2/3 are near saturation, and an overall slowdown explains little of it. The extra ~30 ms on N = 300 small requests is also from this.
  • Do not add per-stage factors to sim: that amounts to modeling GPU slot position.

block rounding

  • HBM was allocated in 8,576-token blocks, wasting an average of 4.3k tokens per context, about 2.4% of HBM.
  • With HBM only and N = 400 right at the capacity edge, this 2.4% decides the result: reducing sim capacity by 2.4% gives 11.2–12.7 r/s and recompute / new token about 1.75, matching the block version on the real engine (12.97 r/s, 1.76).
  • After changing HBM to 128-token pages, each context wastes only 63 tokens; the real engine gives 16.16 r/s and recompute / new token 1.21, landing on the median of sim at full capacity (§5.6).

Steady state after collapse

  • After h25d50 collapses, sim hits drop to zero, while the real engine stays at about 65% DRAM hit rate (§7.1).
  • Real engine: in the collapse window, rounds that hit DRAM start reading 51 / 62 / 68 s after arrival (p10 / p50 / p90), i.e. right at the 60 s forced boundary; once the read lands, this round is admitted before recompute, TTFT is about 64 s, and rounds that lost their context take about 163 s.
  • sim: of the 601 rounds arriving after minute 12, 569 still had their context in DRAM on arrival, but by the time they produced the first token none were left: the context was evicted by LRU 163 / 183 / 189 s after arrival, and no read had started in the meantime.
  • Hypothesis: when sim's staged loading has a whole recompute segment ahead of the overdue queue, it does not start the DRAM read for the overdue round. Not yet confirmed in code (FreshQueues::stage_loads in wt-pp-staged fresh_source.rs, PrefixFetch::stage / load_gate in prefix_fetch.rs).
  • It only affects the period after collapse; the collapse window and everything before match.

Key points

9.1 KDA checkpoints: k1 / k2 / k4 and anchor

  • Two ends: each round has two positions where state can be saved: the end of prefill (end of prompt) and the end of the backfilled decode.

9.2 KDA state compression in tiering

Each layer's KDA state is fp32 [H, 128, 128]. When written to DRAM and SSD it is compressed by a threshold rule: values with |x| < 0.3 are stored as fp16(x · 216) (a power-of-2 scale, the scaling itself is lossless), the rest stay fp32.

  • Compression ratio and error. On 19 real states taken from the SSEngine SSD shard: compression ratio about 1.86x, relative RMS error 1.8e-7, the largest 1% of values lossless. Most heads have max|x| < 0.3, so the whole head can be stored as fixed-length fp16.
  • Comparison: lossless compression (zstd plus byte shuffle) only gives about 1.15x; bf16 of the same size has 8x the error; fp16 without scaling turns about 22% of values into zeros or subnormals.
  • Error does not accumulate. The KDA update is non-expansive with respect to state error (k is a unit vector, β, α ∈ (0, 1)), so compression error is not amplified during the subsequent compute. Checks of the subsequent CPU compute show the error is more than 10x smaller than the noise of the bf16 input itself.
  • Encoding and decoding happen only on the host CPU. At full load the stage's SMs are all busy, and the tiering path uses only the copy engine (§6.1), so no GPU encode/decode is used. State in HBM is not compressed.

  • Writes halved, reads almost unchanged. k2's state writes are 47% lower, SSD writes 35–45% lower. SSD reads are dominated by KV and are almost unchanged, so compression does not relieve read bandwidth.
  • Used on k2 alone the gain is very small (+0.1–1.2%), because k2's writes were not the bottleneck to begin with.
  • It only makes sense together with the anchor. With m2s2 compression, state writes return to k2's uncompressed level, and r/s is 4.0–6.7% higher than k2 (DRAM 150 GB), up to +6.9% (DRAM 220 GB, c2500). Compression on top of the in-place retention anchor adds almost nothing more.

10Conclusions and next steps

  • Scope: this model and hardware, the v3 load, the HBM → DRAM → SSD three tiers, the non-collapsing configuration.
  • Accuracy: the sim's throughput prediction error is 1–5%, and the distribution of hits across the three tiers and the collapse window also line up; every step of bring-up (kernel, single request, simultaneous arrival, prefix, scheduling check, tiered read) matches the target.
  • All gaps were traced to a cause: write cost, hot card, block rounding, host overhead.
  • Better than vLLM: under the same load at N = 400, minutes 0–20, throughput is 5.2x vLLM DP4/EP4 and 19x TP4; TTFT p50 / p90 / p99 0.99 / 4.70 / 61.00 s vs 36.23 / 67.53 / 201.68 s (DP4/EP4) and 147.10 / 333.85 / 346.84 s (TP4).
  • More importantly, the sim let us work out the DRAM and SSD sizes and write patterns, the loading area size, and which optimizations we did not need to do, all before touching anything.
